# F-011 Client Review Access

| **Readiness**    | Implemented                 |

## Context

- **Problem**: A freelancer's client needs to confirm that the approved requirements match what they asked for, without being given an account, a password, or access to anything else in the workspace.
- **Primary Persona**: Client Stakeholder (reviews), Admin and Member (share the access code).
- **In Scope**: A system-generated Project Access Code per project; a public, read-only Client Review Portal that shows a project's approved user stories for a valid code; regenerating a code to revoke it; rate limiting and uniform not-found responses.
- **Out of Scope**: Client accounts or logins, per-stakeholder access control or audit, comments or feedback from the client, expiring or signed links, exports from the portal.

> **Supersedes version 1.x (Viewer Account Management).** The invitation-token flow, Viewer accounts, per-project access grants, and the `viewer` role were removed. See [ADR-020](../04-decisions/adr-020-client-review-by-access-code.md).

## Dependencies and Risks

- **Dependencies**:
  - F-001 Client and Project Lifecycle Management for the project the code belongs to.
  - F-004 Requirements Backlog for the approved stories shown.
  - F-003 Access Control and Visibility Boundaries for the Admin and Member roles.

- **Risks**:
  - **Code shared too widely**: the code is a bearer secret. Mitigation: regenerate (FR-011-06); the portal is read-only and shows approved stories only.
  - **Enumeration**: mitigation is code entropy (NFR-011-01), uniform 404s (FR-011-07), and rate limiting (NFR-011-02). The limiter is per IP and in memory, so shared storage and forwarded-IP handling are follow-ups.
  - **No per-person revocation or audit**: accepted for MVP; revoking means regenerating for everyone.

## User Experience Flows

### Flow 1: Freelancer shares a project with their client

1. Admin or Member opens the project's edit view.
2. They see the access code and click "Copy client link".
3. They send the link or code to their client.

### Flow 2: Stakeholder reviews the approved stories

1. The Stakeholder opens the link, or goes to `/viewer` and types the code.
2. **If the code matches no project**: the page shows "We couldn't find a project with that access code." and keeps what they typed.
3. **If valid**: the page shows the project name, phase, and approved stories with their acceptance criteria.
4. The Stakeholder tells the freelancer, outside the product, whether it matches what they expected.

### Flow 3: Freelancer revokes a code

1. Admin or Member opens the project's edit view and clicks "Generate new code".
2. A confirmation explains that the current code and any shared link will stop working.
3. After confirming, the new code is shown; the old link returns "not found".
