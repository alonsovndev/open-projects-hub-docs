# Glossary

This document defines key terms used throughout the requirements and architecture documentation.

## People and Roles

Only freelancers have accounts. A freelancer's clients and their stakeholders never log in.

**Freelancer**  
The person or business using the platform and the owner of a workspace. The only kind of platform user. A freelancer signs up as the Admin of a new workspace and may add Members.

**Admin**  
The Freelancer who owns a workspace. Full CRUD on clients, projects, and user stories; adds and removes Members; manages API keys; exports requirements. Each workspace has exactly one Admin.

**Member**  
A teammate added by the Admin. Can do everything the Admin can with clients, projects, user stories, and AI refinement, but cannot manage the team or rename the workspace.

**Workspace**  
The tenant boundary: it owns its clients, projects, and stories, and every user belongs to exactly one. A record of another workspace behaves as if it does not exist.

**Client**  
The Freelancer's customer, a person or organization, stored as a record on a project. A Client has no account and never logs in.

**Stakeholder**  
A person at the Client who reviews and validates the requirements. Not stored in the system and has no account: a Stakeholder opens the Client Review Portal with a Project Access Code. A Client can have several Stakeholders, and all of them use the same code.

**End User**  
A user of the software being built for the Client, for example the "clinic patient" in "As a clinic patient, I want...". Appears only inside user stories and personas. Never a platform user.

**Client Review Portal**  
The public, read-only page (`/viewer`) where a Stakeholder enters a Project Access Code to see the project's approved user stories. No login. Shows nothing that identifies the workspace, the Client record, or any user.

**Project Access Code**  
The key a Stakeholder types into the Client Review Portal, for example `PRJ-7K3M9XQ2`. Generated by the system, unique across all workspaces, and unguessable by design. Distinct from the Project Code. The Admin or a Member can regenerate it at any time, which revokes the old code and any link built from it.

## Project Lifecycle

**Active Project**  
Project with status `active`; counts toward the three-project limit shared by a workspace.

**Archived Project**  
Project with status `archived`; does not count toward the active-project limit. Archiving retains the project and its stories; it is distinct from deletion.

**Deleted Project**  
A project removed from persistence, together with its stories. The current implementation performs a hard delete; there is no `deleted` status or support recovery window. See [database deletion behavior](../03-architecture/database/database-design.md).

## User Stories

**User Story**  
Approved requirement in standard format: title + "As a [persona], I want [capability], so that [benefit]" + acceptance criteria. Visible in the Client Review Portal once approved.

**Draft Story**  
Unapproved AI-refined story pending Admin review. Held only in the Admin's browser tab (session storage) and never stored server-side, so it cannot appear in exports or in the Client Review Portal. Can be edited, approved (which saves it as a User Story), or discarded by Admin.

## Epics & Backlog

**Epic**  
A planning grouping used in this repository's work items, such as `EPIC-3`. Epics are not persisted as application entities in the current database; the implemented product stores project stories directly.

**Epic Key**  
Human-readable work-item identifier, such as `EPIC-0`. Story identifiers such as `US-EP0-BE-001` refer to implementation planning artifacts. They are not application record IDs, and Jira integration is deferred.

**Backlog**  
Project view of persisted, approved user stories with status and date filters and Markdown export. Manual reordering and epic grouping are not implemented.

## Projects & Clients

**Project**  
Container for user stories; associated with one Client. Supports discovery and planning phases in MVP; limited to 3 active projects per workspace.

**Project Code**  
Short identifier the Freelancer chooses for a project (for example `WEB`), unique within a workspace only. Used by the Freelancer's own team. Not what a Stakeholder types; see Project Access Code.

**Project Status**  
Enum: `active` (counts toward the limit), `completed`, or `archived` (excluded from the active limit). Deletion removes a record rather than assigning a status.

## AI & Credits

**Platform Provider**  
AI service using the platform's API keys; consumes the user's free credits (5 per Admin or Member). Limited to those refinements unless the user adds their own API key.

**User Provider**  
AI service using the user's own API key (Gemini, OpenAI, or DeepSeek). Does not consume platform credits; provider quotas, costs, and application rate limits still apply.

**AI Refinement**  
Process of submitting raw notes to AI service and generating structured user story with title, standard format, and acceptance criteria.

**AI Credit**  
Unit of platform AI usage; 1 credit consumed per successful refinement using platform provider. Admins and Members receive 5 free credits each on email verification (one-time); a workspace grants at most 25 in its lifetime.

## Authentication & Sessions

**Verification Code**  
Six-character alphanumeric code (excluding ambiguous O/0/I/1) for email verification or password reset. Expires after five minutes for self-registration verification, 24 hours for Admin-added accounts, and 30 minutes for password reset.

**Session**  
Authenticated browser connection using a short-lived access token and a rotating refresh cookie. Refresh sessions use a sliding inactivity window of 24 hours, or seven days with “remember me”; successful refresh extends that window. Access tokens last 15 minutes in the documented deployment.

## Technical Terms

**MVP Load**  
An evaluation target, not a benchmark result: 10 concurrent Admins and 20 client reviewers, 100 requests/minute peak, three active projects per workspace, and 200 total stories (NFR-X05). NFR-X06 separately specifies a 500-story capacity target.

**RLS (Row Level Security)**  
Database-layer access control through PostgreSQL policies. RLS was considered but is not implemented; the application enforces tenant isolation with workspace-scoped repository queries. Client Review derives the project scope from its access code.

**Cross-Cutting NFR**  
Non-functional requirement applying to multiple features; defined in README Cross-Cutting Quality Baseline section (e.g., NFR-X01 through NFR-X10).
